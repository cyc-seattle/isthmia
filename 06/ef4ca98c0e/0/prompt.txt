**What changed, per your comments:**

1. **Rename first.** New step 1 and a dedicated section. The cost is concentrated in five Pulumi resource names. `DirectusSchema`'s delete is a no-op (`directus.ts:144`), but `DirectusRole` and `DirectusUser` really call `DELETE /roles`, `/policies`, `/users` (`directus.ts:266-280`, `:353-356`) — deleting the Staff role would strip it from any user assigned in the Directus UI. `pulumi.Alias` is the right answer and does work for dynamic resources, since the type `pulumi-nodejs:dynamic:Resource` is unchanged. `just preview` must show no creates and no deletes.
2. **Notifications dropped.** No move to `commodore`, no `chat_webhook_url`. The sync writes failures to the sync log and exits non-zero. Listed under "Issues to file".
3. **`person_identities` gone.** Pointers run from `registrations.person_id` and `contacts.person_id` to `people`, resolved once at row creation and never re-resolved — stated explicitly as the reason merges hold. The match is honest about Directus REST: only `_eq` and `_icontains`, no trigram, so it fetches a bounded candidate set by email or last name and compares client-side, with per-kind rules and a deliberate bias toward creating rather than merging. The merge procedure is a documented Directus UI task, and it needs two more o2m alias fields on `people` alongside the existing `guardian_links`.
4. **Gender and address added; weight and school are not Participant fields.** They almost certainly arrive as custom-field responses. `CustomField` is a bare `Parse.Object` (`types.ts:102-109`), and **#90 does not cover it** — #90 scopes Events, Communication, e-signatures, and accounting. So reverse-engineering `customFields` is step 2 of this plan, using the existing generic CLI (`main.ts:109`). Modeled as `custom_field_definitions` + `custom_field_responses`, not a JSON blob, because a blob cannot be filtered or displayed.
5. **`sync_sources` replaced by discovery plus a log.** Club id from `CLUBSPOT_CLUB_ID`. Change detection is four `count()` queries per camp filtered on `updatedAt`, because a camp's own `updatedAt` does not move for child changes. Two holes — `EntryCap` has no camp pointer (`types.ts:338-342`), and deletes never show in `updatedAt` — both closed by a 24-hour refresh floor. Snooze is argued as premature with the numbers. The log is `sync_runs` + `sync_program_runs`, and the watermark is per camp, not per run, or a camp that fails while others succeed loses its window.
6. **Billing in scope.** `registration_billing`, one row per registration, separate from `registrations` for the same permission reason `medical_profiles` is separate. Integer cents, justified by `registrations.ts:26-32`. `docs/crm-schema.md`'s "billing out of scope" section gets updated in step 3.
7. **Open questions replaced** by an "Issues to file" list (capacity panel, notifications) and a single PR of twelve commits.
