**Design decisions worth flagging:**

1. **The `sync_run` task isn't queue-driven.** Discovery failing needs to surface in the same invocation, not get silently retried by the queue's own backoff — conflating "discovery is broken" with "one offering needs a retry" was the trap the design doc warns about, one level up. So `enqueueDueOfferings` calls `queue.enqueue` once (for grouping/UI purposes, via `parent_id`) but drives discovery directly and marks that row `done`/`failed` itself; only `sync_offering` tasks go through `runQueue`.
2. **Failure signal simplified to "not done."** A single-attempt failure leaves a task `pending` (queue-scheduled retry), not `failed` (exhausted). Since `enqueueDueOfferings` resets every offering to `attempts: 0` on every invocation (by the queue's own `planEnqueue` contract), a persistently-failing offering essentially never reaches `attempts &gt;= max_attempts` — it just gets one fresh attempt every scheduled run, matching the old model's "retry forever, once per run" behavior. So `runSync` treats any child task that isn't `"done"` after the drain as this run's failure, rather than only `"failed"`.
3. **`--dry-run` bypasses the queue entirely** (full discovery, direct per-offering loop, same as `--camp`). The queue's own `readItems`/`createItems` dry-run no-op means a dry run's enqueue never persists, so nothing would ever become claimable — going through `runQueue` in dry-run mode would silently do nothing. This is called out in the README.
4. **Skip vs. synced is no longer distinguishable from the task's final status** (`"done"` covers both an offering that wasn't due and one that synced). I treated this as an acceptable loss of granularity given the queue is now the audit trail; flagging it in case that's not the intended trade-off.

**Left alone:** each offering task now re-reads the full shared tables independently (`readSharedTables`), rather than the old single batched read shared across all camps in one run — a natural consequence of per-offering isolation, but a real increase in Directus round-trips for a club with many camps. Not fixed, since it's outside this step's scope and no acceptance criterion calls for it.</result>

**What changed:**
- `readSharedTables` now takes an optional `OfferingScope { clubspotCampId }`. Without it (the `promotePeopleFields` call site), it does the old full 10-collection read — a comment now explains why that pass needs every offering's data.
- With a scope, it reads `offerings` as a single row filtered by `clubspot_camp_id`, resolves the offering's CRM id, and — if the offering already exists — filters `classes`, `sessions`, `custom_field_definitions`, and `registrations` by `offering_id`, then uses those results' ids to filter `session_classes`/`entry_caps` by `class_id _in ...` and `registration_entries`/`registration_billing`/`custom_field_responses` by `registration_id _in ...`. - `_in` is passed as a comma-joined string, which fits the existing `DirectusFilter` type (`string | number | boolean`) without touching `packages/directus`.
- `syncOffering` passes `{ clubspotCampId: camp.id }` into `readSharedTables`; `promotePeopleFields` stays unscoped with a one-line note.

**Before/after read shape**, for a club with N offerings (steady state, each offering already synced once):
- Before: every offering's sync (`readSharedTables`, called once per offering under the queue) issued 10 *full-table* reads — `registrations`, `registration_entries`, etc. — each paginated across the club's entire history. Total: 10 full-collection scans × N offerings, plus 10 more for the one `promotePeopleFields` pass at the end: `10 × (N + 1)` full scans per run.
- After: each offering's sync still issues 10 requests, but 9 of the 10 (everything but `offerings`) are filtered to that one offering's rows via `offering_id`/`class_id`/`registration_id`, so their size and pagination cost is bounded by that offering's own data, not the club's total. `offerings` itself drops from a full-table read to a single-row lookup. The unscoped `promotePeopleFields` pass is unchanged (10 full reads, once per run, not once per offering). Net effect: the per-offering read cost no longer grows as the club accumulates more camps and more registrations over time — the thing issue #135 flagged as unbounded growth is now bounded per offering.

**Deliberately left alone (per scope fence):** `promotePeopleFields` itself reads all 10 collections in full even though `planPromotedFields` only uses `customFieldDefinitions`, `customFieldResponses`, and `registrations` — narrowing that further wasn't part of this brief, so I left it as a full unscoped `readSharedTables()` call, just with the added explanatory comment.
