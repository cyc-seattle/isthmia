**Diagnosis verdict: your mechanism was right, but the specific field was wrong.**

I confirmed the mechanism by reading the actual code that throws: `google-protobuf`'s `struct_pb.js` (`Value.fromJavaScript`), reached via `@pulumi/pulumi/cmd/dynamic-provider/index.js`'s `structproto.Struct.fromJavaScript(resultProps)`. `Struct.fromJavaScript` does `for (var property in obj)` and calls `Value.fromJavaScript` on every own key's value; for a value whose `typeof` isn't string/number/boolean/null/array/object (i.e. `undefined`), it hits `default: throw new Error('Unexpected struct type.')` — the exact message from the failure.

But `externalIdentifier`/`token` are not the culprits. I traced the round trip: `olds`/`news` inside a provider's `create`/`update` come from `req.getOlds().toJavaScript()` / `req.getNews().toJavaScript()`, and `Struct.prototype.toJavaScript` only ever assigns keys that are genuinely present in the wire struct — a field a caller never set (like `externalIdentifier` for the machine user, or `token` for the OIDC user) is simply *absent* from that object, not present with value `undefined`. Spreading `...inputs`/`...news` into `outs` therefore never introduces a literal `undefined`-valued key for those fields. I confirmed this at the source too: `directus-roles.ts` genuinely omits the property key rather than setting it to `undefined`.

The actual culprit is `adopted`. `directusUserProvider.update`'s success path does `{ ...news, userId: olds.userId, adopted: olds.adopted }` — an *explicit* key assignment, not a spread. Both broken resources (`crm-clubspot-sync-user` and `crm-staff-ungood`) predate the `adopted` field, so their persisted state has no `adopted` key at all; reading `olds.adopted` off that state genuinely evaluates to JS `undefined`, and the explicit `adopted: olds.adopted` then creates an own key with that undefined value on `outs` — which is exactly what the protobuf marshaller chokes on. This also explains why both resources failed identically despite being different user types (token vs. OIDC): the shared cause is pre-adoption state, not which optional input field each leaves out. `create()` was never actually at risk in practice, since `upsertUserByEmail` always returns a concrete boolean for `adopted`.

**Fix:** added an exported `omitUndefined` helper that strips undefined-valued own keys from an object, applied to the `outs` returned from both `create` and `update` in `directusUserProvider`. Unit-tested in the new `directus-resources.test.ts` (no HTTP, no Pulumi — pure function).

**Why this can't break `delete`'s three-way `adopted` logic:** `delete` reads `props.adopted !== false` to decide whether to leave the account alone.
