**A genuine design concern I found but left alone, per scope:** bullet 1 of the brief ("collections a package owns outright keep today's behaviour") means a canonical schema's own apply still wholesale-replaces *every* field under a collection it owns outright — including an extension field another package's schema added there. Since provider schemas apply after canonical ones on every deploy (per the justfile, not enforced in code), an outright owner's routine re-apply will drop any sibling's extension field and the provider's subsequent apply recreates it empty, losing that column's data every deploy. This only becomes reachable once step 7 actually adds an extension field (e.g. `programs.google_group_id`), so it's out of this step's scope (no schema changes here), but it's worth deciding on deliberately before that step lands — either accept the destructive round-trip, or give extension fields some real ownership marker. I documented this tradeoff in `applySchema`'s doc comment (in `client.ts`) rather than fixing it, since a real fix needs a design decision beyond "make it field-granular."

I also chose, for extension fields, to preserve rather than delete a field when a provider's own schema stops declaring it — mirroring the existing, deliberate "preserve on drop" behavior for whole collections (#109), since there's no way to safely tell "this package used to own this field and dropped it" apart from "this field belongs to someone else entirely" without an ownership marker the brief didn't ask for.
